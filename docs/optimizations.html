How the Virus Bot Searches

Every search and evaluation optimization in the engine, explained from the actual code — what it is, why it pays in this game, and a picture of the mechanism. Companion to the project overview.

The Virus game is a 12×12 territory game with a twist that shapes every design decision below: each turn grants three actions (GoState.ACTIONS_PER_TURN = 3), so consecutive search plies usually do not alternate players — measured on real games, only 47.1% of moves end a turn and flip the mover. The main engine, GoBotSearcher, is a classic alpha-beta searcher with ~29.6 legal moves per position on average and a 1-second budget per action (PRODUCTION_BUDGET_MILLIS = 1000). A search "ply" is one action, not one turn. Everything below exists to squeeze more decision quality out of that second.

1. Alpha-beta pruning — don't finish refuted moves

What. Plain minimax evaluates every leaf of the game tree. Alpha-beta keeps two running bounds while it searches — α, the score the maximizing side is already guaranteed, and β, the ceiling the minimizing side will allow — and stops searching a node the moment its score can no longer influence the choice above it. Same answer as minimax, a fraction of the work.

Why it pays here. With ~29.6 children per node, an unpruned depth-4 search visits ~770,000 leaves; with perfect ordering alpha-beta needs roughly the square root. In GoBotSearcher.minimax the cutoff is the if (alpha >= beta) break; after each child — and because the root player can move three times in a row, the code is root-relative minimax (maximizing = state.currentPlayer() == root) rather than the textbook negamax that assumes strict alternation. The improvement plan explicitly declined a negamax rewrite: this repo already lost strength once to a score-frame refactor.

The middle subtree is abandoned after one leaf: its minimum is already ≤ 3, and the root has a guaranteed 4. Greyed edges are never generated. The better the first move tried, the more of the tree dies this way — which is why move ordering (next) matters so much.

2. Move ordering — try the likely-best move first

What. Alpha-beta prunes most when the best move is searched first: a strong first child raises α immediately and refutes every sibling cheaply. So before searching, GoBotSearcher.orderedChildren scores each move with heuristic bonuses and stable-sorts descending.

Why it pays here. The bonuses form deliberate magnitude tiers, so a higher tier can never be outvoted by lower ones. The audit behind the current improvement plan found that with the TT move first, most cut-nodes never look past child 1 — the whole point at ~30-wide branching.

The tiers in orderedChildren. Note the game-specific entries: "eliminates a player" (destroying a base or stranding an opponent) and "keeps the turn" — a bonus that only makes sense in a 3-actions-per-turn game, nudging the search to look at plans that retain the initiative.

What's missing is anything learned during the search — no killer moves, no history table. That gap is item 3 of the plan in section 7.

3. PVS — prove siblings worse with a zero-width window

What. Principal Variation Search bets on the move ordering: search the first child with the full (α, β) window, then probe every sibling with a null window (α, α+1) — a window so narrow it cannot measure a score, only answer "is this better than α, yes or no?". A "no" is much cheaper than a full search. A "yes" triggers a full-window re-search to get the real score.

Why it pays here. In GoBotSearcher.minimax that is literally minimax(child, depth-1, alpha, alpha+1, ply+1) followed by a conditional re-search when score > alpha && score < beta (mirrored as (β−1, β) at minimizing nodes — the root-relative frame again). With ~29 siblings behind child 1 and a usually-correct TT move in front, almost all of the tree is these cheap refutations. At the root atDepth flags a fail-low scout result as exact = false so downstream consumers never treat a bound as a real score.

The null window is one point wide, so the search inside it prunes maximally — every node in it is itself a cut-node. The bet loses only when a sibling lands strictly inside (α, β), costing one re-search; good ordering keeps that rare.

4. Iterative deepening — a search you can interrupt honestly

What. Instead of committing to one depth, search depth 1, then 2, then 3… until the budget runs out, and answer with the deepest fully completed iteration. Sounds wasteful; isn't — each iteration is ~branching-factor times bigger than the last, so all previous iterations cost a rounding error, and each one seeds the TT with best moves that make the next one prune far better.

Why it pays here. chooseWithDeadline loops atDepth(state, depth) for depth 1…64 with an absolute epoch-millis deadline; running() checks it (and the optional node budget) at every node and throws SearchIncomplete to abort. The contract — enforced by a dedicated consistency test — is that a partial iteration can never override the last complete one. If not even depth 1 finishes, a preservingFallback action (any legal move that doesn't self-eliminate) is returned. Before any of this runs, GoOpeningBook checks for the one fully-forced phase of the game — the canonical first-turn "wedge" placement — and short-circuits the search entirely.

Each iteration dwarfs the previous one (roughly ×effective-branching-factor), so depths 1–3 together are almost free. Today the partial depth-5 work is thrown away entirely — the plan's time-management item would keep the root moves it finished and skip doomed iterations (don't start d+1 past ~55% of budget).

5. Position hashing — a 64-bit name for every position

What. The transposition table needs a fast fixed-size key per position. Chess engines usually use Zobrist hashing (XOR of per-(cell,state) random numbers, updatable incrementally). This engine does not: GoState.hash() is an FNV-1a hash — start from a constant, then for each byte hash ^= byte; hash *= 0x100000001B3 — recomputed over the full state at every node, byte-for-byte identical to the original GoBot so the two engines' tables agree. The improvement plan looked at switching to incremental Zobrist and declined: the rescan is ~150 cheap operations, dwarfed by the ~60 flood-fills of move generation.

Why it pays here — the 3-actions-per-turn subtlety. The board alone is not the position. Two identical grids are different situations if the mover differs, if the mover has 2 actions left instead of 3, or if a player has already spent their once-per-game neutral-wall placement. So the hash folds in, before the 144 cell bytes: rows, cols, current, movesLeft, and per-player active/neutralUsed flags. Miss any of these and the TT silently returns scores for the wrong situation.

Worked example, three cells through the real mixing function (offset basis 0xcbf29ce484222325):

fold inbytehash after
cell A — owner 1, NORMAL(1<<3)|1 = 90xaf63c44c8601c3c4
cell B — owner 0, EMPTY00x084a5207b4ffa60c
cell C — owner 2, FORTIFIED(2<<3)|3 = 190x15ef82188e6746ad

And the turn-state sensitivity: fold in movesLeft first, then the same three cells — movesLeft=3 gives 0x3b156288202ba440, movesLeft=2 gives 0xc9bd3e906c91a40d. Same board, unrelated keys, exactly as required.

6. The transposition table — never search the same position twice

What. A cache from position key to search result. Positions recur constantly in a search tree (different move orders reaching the same grid — with three actions a turn, placing A then B lands on the same state as B then A), and iterative deepening revisits everything. On a hit at sufficient depth, the stored score answers the node without searching; even on an insufficient hit, the stored best move seeds the ordering.

Why it pays here. The table is a per-search HashMap<Long, TableEntry>; an entry stores {depth, ply, flag, bestAction, score}. Because PVS scores are usually bounds, not exact values, the flag records which: FLAG_EXACT (true score), FLAG_LOWER (score ≥ this — a fail-high), FLAG_UPPER (score ≤ this — a fail-low). The probe in minimax only trusts an entry when entry.depth >= depth && entry.ply == ply, then applies the flag: exact returns immediately, a lower bound can raise α, an upper bound can lower β, and if the bounds cross, the node is answered without generating a single move.

Probe outcomes in minimax. The depth condition says "this cached answer looked at least as far ahead as I need"; the ply == ply condition is a faithfully-ported GoBot quirk that rejects the same position reached at a different distance from the root — one of the defects the overhaul below removes.

7. Landing now — where the audit found the wasted work

The current upgrade wave (docs/plans/20260807-search-strength.md) came out of a line-by-line audit rather than chess-engine folklore. Three items, each behind a single enhanced flag so the GoBot parity fixtures stay untouched.

7a. Staged move generation — stop paying for children you'll never search

What. Today orderedChildren applies every legal action before searching any, because three ordering features (win detection, elimination count, turn continuation) read the child state. Each apply copies the 144-cell grid and runs elimination checks — a full-board connectivity BFS per player. So one interior node pays ~30 grid copies and ~60 flood-fills up front.

Why it pays here. The audit's point: with the TT move ordered first, most cut-nodes cut after child 1 — so at a typical cut-node ~90% of that dominant cost is thrown away. Stage A applies and searches only the TT move first; only if it fails to cut does the node fall back to full generation. Measured baseline (60k-node move, 12×12): hand-tuned leaf searches at ~65k nodes/sec, and the runtime doc itself notes move generation, apply and the TT are "a large share of a node". Expected: node cost ÷2–3, roughly one extra action-ply at equal time.

Pure cost removal — the TT move was already sorted first, so the tree searched is identical. That gives the plan its built-in correctness check: at a fixed node budget the win rate must not move; only fixed time should improve.

7b. Transposition table overhaul — packed arrays, cross-ply and cross-move reuse

The audit verified the key is sound (the turn state is hashed — section 5) and located four real defects: the ply == ply probe rule makes any transposition reached at a different depth-from-root miss, and makes reuse across moves worthless (after playing one action every stored ply is off by one); the whole table is thrown away every move even though the position after our chosen action was the most-searched subtree of the previous search; store overwrites unconditionally, so a shallow entry clobbers a deep one; and HashMap<Long, TableEntry> boxes a key and allocates an entry per store — per node. The fix: a fixed-size array (long[] keys + long[] data, 2²¹–2²³ slots), each entry packed into one 64-bit word, depth-preferred replacement with generation aging, one persistent searcher per game side, and mate scores rebased by ply on store/probe so "mate in 3" stays meaningful from anywhere in the tree.

18 bits fit any action: a move is one cell index 0–143 (8 bits), a neutral-pair placement is two cell indices plus a tag bit. The plan estimates the three compounding effects — allocation-free probes, cross-ply/cross-move hits, no deep-entry clobbering — at +50–100 Elo.

7c. Killers and history — remember what refuted the last sibling

At ~30-wide branching, most cutoffs are quiet positional placements that today sit in raw board order — so the same refutation is rediscovered at every sibling node. Killers keep two recently-cutting moves per ply (Action[64][2], tried right after the TT move); history keeps a score per (mover, target-cell) — int[2][144], bumped by depth² on every fail-high — that gradually learns which squares are hot. The plan's measurement for this is direct: the fail-high-index histogram must shift its mass toward index 0–1. Cheapest Elo in the plan (+40–80 estimated), ranked after 7a/7b only because ordering gains multiply with cheap nodes and warm TT hits.

8. The NNUE sparse trick — a neural net with no matrix multiply

What. The learned leaf evaluator (NNUEv3NetEvaluator) is a tiny one-hidden-layer net over binary features: one feature per (row, col, cell-state), 12×12×8 = 1152 slots. Every position activates exactly 144 of them — one per cell. Since active inputs are all 1.0, the first layer needs no matmul at all: the hidden vector is just the sum of the 144 active columns of W1, plus bias. Then ReLU, dot with w2, done.

Why it pays here. A leaf evaluator runs hundreds of thousands of times per move; this is the discipline that makes a net affordable inside alpha-beta. w1 is stored column-major (w1[feature * hidden + h]) so each active feature's H weights are contiguous in cache. Measured cost is linear in H, ~ 0.4 + 0.08·H µs per eval. (A tempo variant appends 4 movesLeft one-hot slots — 1156 wide, 145 active — the evaluator supports it, but the experiment showed no gain and the shipped net is 1152.)

The forward pass from NNUEv3NetEvaluator.evaluate. Output is already in hand-tuned eval units (the net is distilled from HandTunedEval), so there's deliberately no scaling knob.

The payoff in search terms, from the committed benchmark (60k-node budget, same node count every run, so the ratio is pure speed):

Two readings worth having: the neural leaf is faster than the hand-written eval it imitates (hand-tuned runs its own flood-fills), and search NPS degrades far more slowly than raw eval speed as H grows — from H=4 to H=64 the eval gets 4.7× slower but search only 2.1× — because movegen, apply and the TT dominate the node. That is why section 7a, not a faster leaf, is the current priority.

9. MCTS with PUCT — the other searcher

What. Alongside alpha-beta, the project runs a Monte-Carlo tree searcher (MctsSearcher) as Phase 1 of an AlphaZero-style track. Instead of exhaustive depth-limited search, it grows the tree one simulation at a time, and at each node picks the child maximizing PUCT: an exploitation term Q (average backed-up value) plus an exploration bonus U that favors little-visited moves with high prior probability.

Why it pays here. With ~34 legal actions per state, uniform exploration would drown; the U term concentrates simulations where value or prior points. In select(): score = q + cpuct · prior[a] · √(N+1) / (1 + n[a]) with cpuct = 1.5, priors pluggable (uniform for now), and leaf values tanh(HandTunedEval / 12000) — 12000 chosen so a typically decisive mid-game eval (~13k) maps to ≈0.8. Dirichlet root noise exists for future self-play but is off in play mode.

The self-balancing property: every visit to C divides its bonus, so bad moves are abandoned after a handful of simulations while good ones accumulate visits — and the final answer is simply the most-visited root move (bestAction()).

10. Absolute-frame backup — the hardest-won lesson in the repo

What. Standard two-player MCTS (and negamax) backs values up the tree negating at every edge: "good for me" is "bad for you", and every edge changes whose turn it is. In this game that assumption is false — each edge is one action, and only 47.1% of them end a turn. Negate on every edge and you flip the sign on the 52.9% of edges where the same player is still moving.

Why it's done this way — the bug that forced it. The v3 training pipeline hit exactly this class of error: children were labelled from the parent's mover while the runtime queries the leaf's own mover, inverting the sign on the 47.1% of turn-flipping children. The hand-tuned eval hates ending your turn (turn-keeping children average +6,958, turn-flipping −14,108, and the best child is a flipper in only 1.0% of sibling groups), so after the runtime's negation the net ranked precisely the worst moves best: sibling-ordering correlation ρ = −0.298 — worse than random — versus +0.756 once the frame was fixed. MctsSearcher makes that mistake structurally impossible: every value is converted once, at the leaf, into a fixed absolute frame (positive = good for player 1), backed up with no negation anywhere, and re-oriented only at selection time via sign(node) = +1 iff node's mover is player 1. The alpha-beta searcher sidesteps the same trap differently — root-relative minimax with a single mover-vs-root flip at the leaf.

Both backups agree on flip-turn edges; on keep-turn edges only the absolute frame is correct. Converting at the leaf (v_abs = mover == 1 ? v : −v, terminals ±1/0 from outcomeWinner()) means the tree never needs to know which edges flipped.

11. Measurement discipline — why only big gauntlets count

The uncomfortable meta-result of this project: offline metrics have repeatedly failed to predict playing strength — by the docs' own running count, six documented disconnects and counting. The greatest hits:

looked great offlineplayed
v2: val MSE 0.018, 97% direction accuracy0–24 (0%)
v3 linear: held-out R² = 0.976 vs its target7–17 (29.2%)
frame fix: sibling ordering ρ −0.298 → +0.756no measurable strength change
retrain on 2.6× data: live-frame top-1 77.5% → 86.6%52.0% ± 2.5 head-to-head — a tie

Each failure taught a sharper metric — R² gave way to sibling top-1 agreement, which gave way to the live-frame probe — and each sharper metric still failed to predict the gauntlet. So the project's rule hardened into policy:

A strength claim requires a gauntlet of 400+ games with disjoint opening seeds. At 24 games the noise on a win-rate difference is about ±10 points — the historical 24-game cells produced per-depth numbers that literally swapped values between runs. At 400 games the 95% interval tightens to ~±5 points (reported results above carry ±2.1–2.5 standard error).

Two supporting habits make those numbers trustworthy. Disjoint openings: GauntletMatch derives openings from the seed, and an audit found "robust across seeds 7/11/23" runs actually shared 8 of 12 opening pairs — seed ranges are now spaced 1000 apart. Fixed-node vs fixed-time: speed optimizations (sections 7a/7b) must show ~zero effect at a fixed node budget (they don't change the tree — a built-in correctness check) and their real gain at fixed wall-clock; ordering improvements (7c) must win at fixed nodes. Every item in the current plan is scheduled to be measured both ways before it's believed.
